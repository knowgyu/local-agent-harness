## 설계자가 판단하도록 맡긴 항목

사용자는 인증 방식의 장단점을 아직 판단하기 어렵다고 답했다. 따라서 OAuth를 사용자 선호로 기록하지 않는다.

제안 H01: **토큰 발급 안내를 우선 제공하고, 지원이 검증된 경우에만 브라우저 인증을 추가한다.** 기존 저장 비밀 참조가 적절하면 직접 선택할 수 있게 한다. 회사가 지원하지 않는 OAuth를 필수로 만들지 않는다.

## 아직 검증하지 않은 가설

| ID | 가설 | 검증 방법 |
| --- | --- | --- |
| H02 | 첫 등록은 단계별 안내, 반복 수정은 한 화면 순차 확장이 편함 | 같은 서비스 과제로 A/B 관찰 |
| H03 | URL 해석 후보와 수정 경로가 재입력을 줄임 | origin·리소스를 이해하고 수정할 수 있는지 확인 |
| H04 | 첫 조회까지 이어주는 다음 행동이 탐색 부담을 줄임 | 연결 저장 후 도움 없이 AI 앱과 첫 요청을 찾는지 확인 |
| H05 | 실패 시 일반 설정을 보존하면 중단 후 복귀가 쉬움 | 앱 재시작·승인 대기·토큰 만료 시나리오 |
| H06 | 데모에서 성공·실패를 연습하면 실제 설정을 이해하기 쉬움 | 데모와 실제 성공을 구분하는지 확인 |
| H07 | 대상·허용 작업에 집중한 범위 검토가 반복 확인보다 유용함 | 잘못 추론된 리소스와 추가 실행 권한을 발견하는지 확인 |

대화형 AI 등록은 선택 보조안이며 기본 흐름으로 확정하지 않았다. 화면 스타일·색·타이포그래피 재설계도 아직 확정하지 않았다.

| GitHub Enterprise 서버 버전과 정책 | 버전별 안내 분기·권한표 구조 설계 | 사용 가능한 토큰 종류·조직 승인·실제 endpoint 권한 |
| Jenkins 버전·context path·권한 정책 | 중첩 작업 URL fixture와 계정/API 토큰 안내 | 발급 메뉴·작업 읽기 권한·프록시 응답 |
| Dashboard 설치 track·프록시 및 수정 여부 | 구형 전체 v1.7.0 소스 기반 fixture와 버전 식별 계약 | chart/API/auth 이미지, 토큰 전달·헤더 변환·조회 권한·TLS |
| Desktop 설치·실행 환경 | 공식 지원 경로와 현재 CLI 구현 비교 | 같은 host의 공유 설정 인식, 실제 대화의 도구 호출 |

미확인 사내 정보를 당장 얻지 못해도 URL 해석, 인증 도움말 구조, 초안 상태, 합성 데모와 테스트 설계는 진행할 수 있다. 다만 실제 환경 성공이나 Desktop 연결 검증 완료로 보고하지 않는다.

## 구현 전 확인 기준

- [ ] 세 서비스 모두 첫 읽기 과제와 불필요한 권한이 정리되어 있다.
- [ ] Dashboard 실제 backend 식별 절차와 설치별 인증 계약이 정해져 있다. 구형 태그 Bearer/JWE 불일치의 적용 범위를 구분한다.
- [ ] ChatGPT Desktop·Claude Desktop·CLI의 설정 범위와 실제 검증 상태가 구별된다.
- [ ] 초안 저장 데이터와 비밀 저장 계약, 삭제·이어하기·상태 무효화가 정해져 있다.
- [ ] A/B 화면안에서 URL 입력부터 첫 조회까지 비교할 수 있다.
- [ ] 새 검사 계획이 기존 유의미한 테스트를 재사용하고 필요한 차이만 추가한다.

이 체크리스트는 승인 요청이나 자동 차단 규칙이 아니다. 다음 구현을 구체화하기 위한 설계 검토 항목이다.
