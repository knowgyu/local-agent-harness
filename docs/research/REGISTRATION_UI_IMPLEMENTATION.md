# Registration UI implementation record

Date: 2026-10-12. Scope: the production onboarding flow for GitHub Enterprise, Jenkins, and Kubernetes Dashboard targets in `ui.html`.

## Selected production flow

New connections use the guided URL-first flow. The common Connections entry asks for one service and an HTTPS service, repository, or job address. The address is sent only after the user chooses **Check address**. Choosing a service or changing the address only invalidates this independent preview; it does not clear credentials or a check permit on an active draft. The local parser returns a shape-based candidate; the UI shows the inferred values, URL-derived missing information, and fields that need review. It uses localized labels rather than exposing wire keys.

The user must explicitly apply the reviewed candidate to the matching target form. Applying it overwrites only that service's URL-derived fields, including clearing a field when the new candidate leaves it empty; the target name, credentials, and other service forms stay untouched. If a saved target is loaded, a second explicit confirmation clears only unsaved values in that service form and switches to a new target. Applying a candidate does not save settings, store a secret, run a connection test, or contact an external service.

After applying a candidate, the operator can save ordinary fields as guided progress, even while incomplete, or use the existing manual save action. A short notice explains that manual save does not run a connection check. Guided drafts can normally be reopened or deleted until activation starts; at most five can be retained. Drafts store normalized service fields, including the normalized address, but never the pasted source text, temporary credential, named-credential reference, or check permit. Reopening clears credentials and the permit. A historical check receipt is shown for context only; it never authorizes activation. Existing manual edits to saved targets retain their current behavior.

The guided flow provides service-specific help for preparing a GitHub Enterprise token, Jenkins username/API token, or Dashboard Bearer value. The user pastes the temporary credential or chooses a named credential for a one-request connection check. No service version is inferred: in particular, Dashboard's displayed `1.7.0` does not identify its product or authentication contract. The local connector sends the configured value as Bearer authentication and performs no login exchange or version detection.

The credential hint distinguishes the two save paths: a guided draft never stores the pasted value, and confirmed activation stores it in Windows Credential Manager; the separate immediate-save action stores it when the user saves. Dashboard copy says the value is sent unchanged as Bearer authentication, that this UI does not log in, exchange tokens, or detect a version, and that the required value depends on the installed Dashboard or proxy and must be confirmed with its administrator or version documentation.

After a successful check, the UI shows a fixed operation-scope review tied to that check generation and the current policy/configuration revision. The user confirms the review before explicit activation. Any draft field, credential, credential choice, draft switch, reload, or permit expiry requires a fresh check; the review and activation controls stay disabled until the current check is valid. A durable `activation_recovery_required` state is different from ordinary `activation_pending`: it means credential storage or cleanup needs manual investigation. The list identifies the blocked draft. Opening it is read-only and uses the normal form-switch confirmation before switching away from another active draft; that draft offers no save, check, review, activation, delete, or retry path. Other saved drafts, new targets, and manual edits remain independent. The operator must inspect the target in Settings and its Windows Credential Manager entry. By contrast, `activation_pending` remains recoverable by refreshing a still-available draft and running a fresh check.

After activation, the UI says plainly that it saved the target but did not run the separate connection test or an AI-app read. It links to the existing test and AI-app setup guide, offers a service-specific read-only request that is copied rather than executed, and points to Readiness for verifying an actually observed first read. Neither activation nor copying that example claims that an external read occurred.

That completion handoff stays visible until the user applies the next URL candidate to a new target; activation completion does not keep unrelated new-target draft-save actions disabled. The separate client guide covers CLI registration inspection and manual desktop setup. Claude Desktop has a local preview MCPB package and instructions in `docs/CLAUDE_DESKTOP.md`; package checks passed, while actual installation, launch, tool visibility, and an MCP call remain unverified. Switching language also re-renders the displayed historical check outcome and timestamp in the selected locale.

The server-rendered “no targets yet” message is hidden only after the activation response passes its receipt checks. The settings form's saved-target selectors remain server-rendered until the user follows the result's target link or reloads, so the completed handoff remains accurate without displaying a false empty state.

Responses are ignored if the service or address changed while a URL preview was in flight. Returned values render as text, not HTML. The UI does not persist URL preview state in browser storage.

## Local preview contract

The production UI calls `POST /preview-registration-url` with `application/x-www-form-urlencoded` and exactly these fields: `csrf`, `service`, and `url`. Service values are `github`, `jenkins`, or `dashboard`. The endpoint uses the existing same-origin/CSRF checks and returns either a `candidate` with `origin`, `repository`, `base_url`, `job_path`, `missing_fields`, and `review_fields`, or a fixed error code. It parses locally; it does not resolve or fetch the supplied host, access the target's credential, read or write settings, or call a service.

The parser accepts HTTPS addresses without user information, query, or fragment. GitHub candidates use the origin and repository path when present; the service origin alone reports the repository as missing. Jenkins candidates identify a base path and canonical terminal `/job/<name>` chain when possible, and flag inferred base/job splits for review; a base-only address reports the job path as missing. Dashboard candidates retain the entered path in the suggested base URL and flag it for review. These are suggestions from URL shape, not proof of an installed component, resource, route, or permission.

The existing save handlers and target validation remain authoritative. The new registration preview does not change authentication transport, stored credential semantics, permissions, supported operations, or saved-target defaults.

## Authentication and evidence boundaries

For Dashboard, the UI states that this connector sends the stored value as `Authorization: Bearer`, performs no login or token exchange, and cannot identify which Dashboard component or version is installed. The reported `1.7.0` display does not establish an authentication contract. The UI asks the user to verify the expected credential for the installed service or proxy and does not present `/api/v1/login` output as a value that can be copied blindly.

After activation, users may run the existing connection test, then follow the AI-app setup guide and verify a read inside the active app. A successful service test is not evidence of an AI app's first read. The production UI contains no synthetic first-read outcome and makes no unsupported desktop compatibility claim.

The archived A/B comparison in [`REGISTRATION_DESIGN_BRIEF.md`](REGISTRATION_DESIGN_BRIEF.md) and [`prototypes/registration-options.html`](prototypes/registration-options.html) remains a comparison of two synthetic **new connection** flows. Prototype B is not the production edit-existing-target screen. Synthetic permissions, credentials, and first-read states in that prototype are not current product behavior.
